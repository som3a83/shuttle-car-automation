# Shuttle Car Automation 1.0.0

A bilingual, offline-first operational workspace for recording and reviewing industrial shuttle-car fleets. Built with React 18, TypeScript, Vite, Capacitor 8 and Three.js.

> **Release scope:** this is a device-local operational application with an optional HTTPS client for a separately deployed read-only OT gateway. No physical shuttle is connected by default, no vendor driver is bundled, and the app never sends machine-control commands. It is not a safety system.

## Application workspaces

- **Dashboard:** operational overview sourced from the current local records.
- **Fleet:** register, edit, search, archive and restore shuttle assets.
- **Batteries:** battery register, manual measurements, installation/reassignment, archive/restore and movement journal.
- **Shift operations:** day/night shift opening, fleet snapshot, supervisor/operator names, handover notes and saved local history.
- **Engineering:** interactive Three.js reference assemblies with selectable components and orthographic views. Editable OpenSCAD source models and STL validation artifacts are maintained in the cad folder; default dimensions are illustrative, not OEM-certified.
- **Faults and diagnostics:** manually reported observations, editable records, corrective-action documentation, investigation/resolution workflow, and resolved-only archive/restore.
- **Maintenance:** local work-order creation and editing, scheduled/in-progress/completed tracking, mandatory recorded completion results for new completions, completed-only archive/restore, and completion-result Excel export. Unfinished work cannot be hidden by archiving.
- **Connections:** universal transport/protocol register, native Bluetooth LE GATT read-only explorer, plus an optional HTTPS client for an approved read-only OT gateway. The BLE explorer can scan/connect/discover/read raw GATT characteristics (and subscribe to notifications) on a physical mobile device; raw payloads are not treated as verified shuttle telemetry until the vendor UUID/tag mapping and decoder are commissioned. The generic gateway includes read-only Modbus TCP and Modbus RTU serial adapters, plus TLS-capable generic MQTT, certificate-secured OPC UA and read-only REST API clients; Modbus still requires the exact OEM-approved register map and MQTT requires the exact approved topic/payload contract. The app does not scan or probe PLC networks.
- **Application customization:** locally saved module visibility, navigation labels/groups/order, aliases to existing routes, dashboard widget visibility/order/size, and restoration of default preferences. This is device-local customization, not authentication or secure authorization.
- **Technical assistant:** static inspection checklist, not a connected AI service or certified diagnosis.
- **Reports:** daily snapshots with per-report CSV/XLSX export and confirmed local deletion, multi-sheet register XLSX/CSV exports, JSON backup and browser print/Save as PDF.
- **Notifications:** local notifications generated by changes to local records.
- **Users and settings:** role preview, Arabic/English, dark/light themes, backup/restore and local data inventory.

## Parametric CAD source

The cad folder contains editable OpenSCAD reference assemblies for the shuttle frame and lithium battery pack. GitHub Actions compiles both sources to STL on pull requests and publishes the source plus rendered meshes as a workflow artifact. The model defaults are illustrative design-study values only; obtain and use serial/model-specific OEM drawings before any fit check, fabrication or service decision.

## Data lifecycle and local records

- Equipment, batteries, faults, work orders and connection-register entries are local records. Removal from active screens uses soft archive where history matters; restore returns the same record.
- Fault reports may be archived only after resolution. A corrective action is required before a fault can be resolved.
- Work orders may be archived only after completion. Scheduled, in-progress and overdue work remains visible.
- Connection-register entries remain documentation placeholders. Live telemetry requires the separately deployed `industrial-gateway` service, an exact vendor-specific adapter, and an approved read-only commissioning. The gateway read token is held in the screen session memory only and is not persisted to localStorage.
- Daily report snapshots are frozen at generation time. Each snapshot can be exported as CSV/XLSX or deleted after confirmation.
- The customization activity list and preferences are mutable local-device data. They are not a tamper-proof audit trail and are not server-enforced permissions.

## Android debug build

The GitHub Actions workflow **Build Android Debug APK** creates a Capacitor Android project, generates branded Android icons/splash resources, syncs the web bundle and builds a debug APK. It then attempts an emulator install/launch check and uploads the APK and evidence separately.

A successful APK assembly does **not** prove emulator or physical-device runtime success. The latest matching Actions run is the authoritative result.

The separate **Package Android Debug APK** workflow packages the installable debug APK and SHA-256 checksum for local evaluation. A debug APK is not the signed Google Play upload artifact.

## Google Play release

The release workflow is **Android Play Store AAB**. It produces a signed Android App Bundle (AAB) only after a publisher-provided upload keystore and GitHub Actions secrets are configured.

Required repository Actions secrets:

- `ANDROID_KEYSTORE_BASE64`
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

Create the upload key and configure it using the instructions in [PLAY_STORE_RELEASE.md](PLAY_STORE_RELEASE.md). Do not commit signing keys, passwords, certificates or production credentials.

The release workflow enforces compile/target SDK 36, runs TypeScript/tests/build, generates branded Android resources, builds a signed AAB and signed release APK using the publisher upload key, verifies both signatures and produces SHA-256 checksums. It does not upload to Google Play automatically.

## Local application customization

The in-app **Customize** control opens a device-local presentation settings center. It can:

- Enable or hide supported non-critical modules without deleting their data.
- Change existing navigation labels in English and Arabic, groups, visibility and order.
- Add or remove menu aliases that point only to an existing supported application route.
- Show, hide, resize and reorder the supported dashboard widgets.
- Restore default presentation preferences and review a local customization event list.

The dashboard and desktop/mobile navigation consume these saved preferences. Core routes (Dashboard, Fleet and System Settings) cannot be hidden or disabled. Unknown routes and malformed preference values are discarded when settings are loaded.

**Security and storage boundary:** preferences, local identities, audit events and operational snapshots remain on the current device. The app now has local account sign-in, a role-permission matrix, application-level mutation checks, PBKDF2-SHA-256 password derivation, expiring local sessions, a SHA-256 chained audit log, and versioned/checksummed storage with recovery snapshots. These improve local separation and corruption detection but are not immutable or server-enforced security: a person who can modify app/browser storage or application code may bypass them. Hiding a menu item is never treated as authorization.

## Data storage and privacy

The current version stores operational records, local account metadata and audit data in local browser/WebView storage on the current device. Local sign-in is available, but there is no shared cloud database, trusted identity provider, app-operated backend, server-enforced RBAC or cross-device synchronization. Local roles are enforced in application logic only and must not be treated as a server security boundary.

Exported JSON, CSV and XLSX files may include equipment information, staff names and operational notes. Protect exported files and the device. Local browser storage is not application-level encryption; do not enter passwords, API keys or highly sensitive secrets.

See [PRIVACY_POLICY.md](PRIVACY_POLICY.md) for the current data handling notice. The publicly reachable policy page for the current branch is: https://github.com/som3a83/shuttle-car-automation/blob/main/PRIVACY_POLICY.md.

## Local identity and storage integrity

- First launch presents a local administrator bootstrap; after an account exists, the app starts in guest mode until a valid local session is restored or a user signs in.
- Passwords are not stored in plaintext. Local accounts use PBKDF2-SHA-256 derived values with per-account random salts. This protects stored password material but does not make browser storage tamper-proof.
- Operational collections are migrated at startup into revisioned SHA-256-checksummed envelopes. The previous verified snapshot is retained; damaged envelopes are quarantined and reported rather than silently treated as clean data.
- Local audit entries are chained with SHA-256 and verification fails closed on malformed or modified entries. This is a local tamper-evidence mechanism, not an externally immutable audit service.
- The versioned store supplements the legacy localStorage keys for compatibility. It is not SQLite and is not a substitute for a managed database in a multi-device deployment.

## Industrial connectivity and safety boundaries

- The Connections workspace includes a native Bluetooth LE GATT raw-data explorer and an optional HTTPS client for a separate read-only OT edge gateway. It does not open PLC sockets or scan plant networks.
- The Python read-only gateway is in [industrial-gateway](industrial-gateway/README.md). It exposes authenticated status/read APIs and a separate authenticated telemetry-ingest route for approved adapters. The gateway accepts arbitrary manufacturer names and exact model/firmware registrations; it is not hard-coded to the current five-asset fleet. The generic Modbus TCP adapter is implemented; its register map must be issued/approved for the actual machine.
- A universal transport/protocol catalog and its implementation status are documented in [UNIVERSAL_CONNECTIVITY.md](UNIVERSAL_CONNECTIVITY.md). This development branch adds a generic read-only Modbus TCP adapter. It still requires the exact OEM-approved register/tag map for the target model.
- The gateway ships with the five known asset identities, but every asset is disabled and uncommissioned. Exact model, controller/firmware, adapter identity and the manufacturer-approved tag map must be documented before readings are accepted.
- No manufacturer-specific Cassioli, Craftsman or ACME driver is supplied yet. The generic Modbus TCP adapter can only be used when the exact shuttle controller supports Modbus TCP and the OEM-approved register map is available. Bluetooth, serial, proprietary radio and other protocol entries are extension points until their native/edge drivers are implemented and tested. Therefore no physical shuttle is connected by this code change alone.
- The app accepts a gateway read token for the current screen session only; it is not persisted to localStorage. Plant access must use HTTPS, network segmentation and the approved VPN/identity layer.
- Battery SOC/SOH, voltage, current, temperature, cycles and shuttle status remain manual, simulated or unknown unless a fresh, good-quality sample comes from a commissioned vendor adapter.
- Do not invent register maps, device addresses, network parameters or vendor credentials.
- The 3D shuttle and battery assemblies are conceptual engineering illustrations, not manufacturer CAD, service drawings or dimensionally verified models.
- The application does not send movement, charging, PLC-write or machine-control commands.
- The technical assistant provides static guidance only and must not be treated as a qualified diagnosis.
- Do not use the application as an emergency-stop, safety, machine-protection or release-to-service system.

Before any hardware integration, obtain written authorization, manufacturer-approved interface documentation, protocol/register specifications, network topology and safety constraints. Begin with read-only telemetry and verify every field against approved documentation and the physical HMI.

## Release gate

A store submission is **not complete** until all of the following have been done:

1. CI TypeScript, tests and production build pass on the exact release commit.
2. Android bundle builds and the signed AAB signature/checksum are verified.
3. Emulator test passes and the signed release is tested on at least one physical Android device.
4. The publisher has configured and safely backed up the upload key.
5. Public HTTPS privacy-policy URL, support contact and Play Console declarations are completed.
6. 512 × 512 icon, 1024 × 500 feature graphic and genuine app screenshots are uploaded.
7. Store content rating, target audience, data safety, app access, ads and distribution forms are completed truthfully.
8. The publisher uploads the signed AAB to Play Console and completes the chosen testing/production rollout.

See [PLAY_STORE_RELEASE.md](PLAY_STORE_RELEASE.md) for step-by-step instructions.
