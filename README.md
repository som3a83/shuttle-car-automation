# Shuttle Car Automation 1.0.0

A bilingual, offline-first operational workspace for recording and reviewing industrial shuttle-car fleets. Built with React 18, TypeScript, Vite, Capacitor 8 and Three.js.

> **Release scope:** this is a device-local operational recordkeeping application. It is not connected to physical shuttles, PLCs, battery-management systems or vendor gateways. It does not send machine-control commands. It is not a safety system.

## Application workspaces

- **Dashboard:** operational overview sourced from the current local records.
- **Fleet:** register, edit, search, archive and restore shuttle assets.
- **Batteries:** battery register, manual measurements, installation/reassignment, archive/restore and movement journal.
- **Shift operations:** day/night shift opening, fleet snapshot, supervisor/operator names, handover notes and saved local history.
- **Engineering:** interactive Three.js conceptual shuttle and lithium-battery assemblies with selectable components and camera views.
- **Faults and diagnostics:** manually reported observations, corrective actions and closure validation.
- **Maintenance:** local work-order creation and status tracking.
- **Connections:** reference architecture for Modbus TCP, OPC UA, MQTT, REST, WebSocket and BLE; no endpoints are configured.
- **Technical assistant:** static inspection checklist, not a connected AI service or certified diagnosis.
- **Reports:** immutable daily snapshots, multi-sheet XLSX exports, CSV exports, JSON backup and browser print/Save as PDF.
- **Notifications:** local notifications generated by changes to local records.
- **Users and settings:** role preview, Arabic/English, dark/light themes, backup/restore and local data inventory.

## Supported languages and navigation

- Arabic RTL and English LTR.
- Dark and light themes.
- Responsive phone, tablet and desktop layouts.
- URL-hash navigation with browser back/forward and in-app home/back controls.
- Branded launcher and splash artwork generated during native Android builds.

## Validate

```bash
npm audit --audit-level=high
npm run check
npm test
npm run check:release
npm run assets:render
npm run build
npm run validate
```

- `npm audit --audit-level=high`: fail CI for high/critical known dependency vulnerabilities.
- `npm run check`: TypeScript project check.
- `npm test`: Vitest regression suite.
- `npm run build`: production Vite bundle.
- `npm run assets:render`: creates Google Play listing PNGs and PWA icons from the vector artwork.
- `npm run check:release`: tests the API 36/version/signing Gradle configuration using temporary fixtures.
- `npm run validate`: runs the complete dependency, type, test, release-config, asset and production-build checks.

The current GitHub CI runs these commands on the feature branch and the main branch. Read the matching commit's workflow result before treating any test/build as passed.

## Android debug build

The GitHub Actions workflow **Build Android Debug APK** creates a Capacitor Android project, generates branded Android icons/splash resources, syncs the web bundle and builds a debug APK. It then attempts an emulator install/launch check and uploads the APK and evidence separately.

A successful APK assembly does **not** prove emulator or physical-device runtime success. The latest matching Actions run is the authoritative result.

The separate **Package Android Debug APK** workflow packages the installable debug APK and SHA-256 checksum for local evaluation. A debug APK is not the signed Google Play upload artifact.

## Google Play release

The release workflow is **Android Play Store AAB**. It produces a signed Android App Bundle (AAB) only after a publisher-provided upload keystore and GitHub Actions secrets are configured.

Required repository Actions secrets:

- `ANDROID_KEYSTORE_BASE64`
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

Create the upload key and configure it using the instructions in [PLAY_STORE_RELEASE.md](PLAY_STORE_RELEASE.md). Do not commit signing keys, passwords, certificates or production credentials.

The release workflow enforces compile/target SDK 36, runs TypeScript/tests/build, generates branded Android resources, builds `bundleRelease`, verifies the signature and produces a SHA-256 checksum. It does not upload to Google Play automatically.

## Local application customization

The in-app **Customize** control opens a device-local presentation settings center. It can:

- Enable or hide supported non-critical modules without deleting their data.
- Change existing navigation labels in English and Arabic, groups, visibility and order.
- Add or remove menu aliases that point only to an existing supported application route.
- Show, hide, resize and reorder the supported dashboard widgets.
- Restore default presentation preferences and review a local customization event list.

The dashboard and desktop/mobile navigation consume these saved preferences. Core routes (Dashboard, Fleet and System Settings) cannot be hidden or disabled. Unknown routes and malformed preference values are discarded when settings are loaded.

**Security and storage boundary:** these preferences and their event list are stored in local browser/WebView storage on the current device. They are editable by anyone with access to that device and are not an immutable audit trail, authentication mechanism or server-enforced role-based authorization. Hiding a menu item is presentation only; it does not secure the underlying data or route. The current application remains local-device recordkeeping software without a shared backend or authenticated server.

## Data storage and privacy

The current version stores records in local browser/WebView storage on the current device. There is no shared cloud database, app-operated backend, authentication service, server-enforced RBAC or cross-device synchronization. The role selector is a UI preview only.

Exported JSON, CSV and XLSX files may include equipment information, staff names and operational notes. Protect exported files and the device. Local browser storage is not application-level encryption; do not enter passwords, API keys or highly sensitive secrets.

See [PRIVACY_POLICY.md](PRIVACY_POLICY.md) for the current data handling notice. The publicly reachable policy page for the current branch is: https://github.com/som3a83/shuttle-car-automation/blob/copilot/complete-shuttle-automation-v6/PRIVACY_POLICY.md.

## Industrial connectivity and safety boundaries

- No live PLC, manufacturer API, gateway or telemetry endpoint is configured.
- Battery SOC/SOH, voltage, current, temperature, cycles and shuttle status are manual, simulated or unknown unless a verified source is explicitly identified.
- Do not invent register maps, device addresses, network parameters or vendor credentials.
- The 3D shuttle and battery assemblies are conceptual engineering illustrations, not manufacturer CAD, service drawings or dimensionally verified models.
- The application does not send movement, charging, PLC-write or machine-control commands.
- The technical assistant provides static guidance only and must not be treated as a qualified diagnosis.
- Do not use the application as an emergency-stop, safety, machine-protection or release-to-service system.

Before any hardware integration, obtain written authorization, manufacturer-approved interface documentation, protocol/register specifications, network topology and safety constraints. Begin with read-only telemetry and verify every field against approved documentation and the physical HMI.

## Release gate

A store submission is **not complete** until all of the following have been done:

1. CI TypeScript, tests and production build pass on the exact release commit.
2. Android bundle builds and the signed AAB signature/checksum are verified.
3. Emulator test passes and the signed release is tested on at least one physical Android device.
4. The publisher has configured and safely backed up the upload key.
5. Public HTTPS privacy-policy URL, support contact and Play Console declarations are completed.
6. 512 × 512 icon, 1024 × 500 feature graphic and genuine app screenshots are uploaded.
7. Store content rating, target audience, data safety, app access, ads and distribution forms are completed truthfully.
8. The publisher uploads the signed AAB to Play Console and completes the chosen testing/production rollout.

See [PLAY_STORE_RELEASE.md](PLAY_STORE_RELEASE.md) for step-by-step instructions.
